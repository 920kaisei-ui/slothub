# GemCrash 完成度向上の調査と検証手順

## ① 調査から適用案まで

1. **機種別資料を確認する。** スロットとパチンコを各5機種とする。各機種の通常時、転機、転機の結果、通常への復帰を特定し、画面の視線誘導、音の区切り、演出の開始条件と終了条件を確認する。型式違い・海外版・別年式の情報は混ぜない。
2. **証拠の種類を分ける。** 公式仕様はルールの根拠とする。映像の視聴記録はURL・区間・観察内容を残す。静止画、動画の説明文、字幕、音声の実聴は別の根拠として記録する。攻略記事や投稿は個人の観察や感想として扱い、結果の保証や全体傾向には使わない。
3. **横断して比較する。** 複数機種で見られた共通点と、その仕掛けが機能する条件を示す。例外や反対の反応があれば、その出典も記録する。作品固有の素材は参照にとどめ、抽出した仕組みをGemCrashの宝石と連鎖に置き換える。
4. **10案を検証する。** 各案に固有の観点、プレイ中の発動条件・見え方・終わり方、採用根拠、GemCrashへの適用可否、確認方法を持たせる。似た目的の案があれば統合し、異なる目的の案で補う。映像や音声を確認できなかった場合は参照先を探し直し、不足を明記する。

## ② 変更ごとの検証

各変更は、着手前に「作業履歴」の次の作業として記録する。完了時には、採用した案、試験条件、結果、点数と根拠、次に適用する案を同じ履歴に追記する。

採点には①の横断分析で抽出した評価軸を使う。軸ごとの試験は、画面や操作で何を観察できたかを基に判定する。

| 点 | 判定 |
| --- | --- |
| 0 | 期待する体験を実現していない。または機能上の破綻がある |
| 1 | 部分的に成立するが、意図を読み取るには説明や回避操作が必要 |
| 2 | 通常の流れでは成立する。端末差、境界条件、互換性の確認が残る |
| 3 | 指定した操作と境界条件で成立し、目的の情報が操作中に読み取れる |
| 4 | 3を満たし、別の入力・表示条件でも成立することを実機または同等の確認で実証した |

未確認と対象外には点を付けず、理由を記録する。変更対象の軸が3点未満の場合は、改修と再検証を優先する。判断の根拠として固定盤面や同じ乱数列を使い、盤面ロジック・確率・配当への意図しない変更はシミュレータの一致で検出する。

## ③ 回転と停止の動き

②の適用と評価を終えたあと、入力から回転、列ごとの制動と停止、確定盤面への接続を作る。停止先には共通エンジンが生成した盤面を使う。見かけの回転帯にゲーム用乱数を消費させず、停止順や速度、スキップ操作で配当が変わらないことを確認する。端末で通常と短縮を比較し、動き軽減では盤面と結果を即時に読めるようにする。

## ④ 画像素材の組み込み

③の動きを確認したあと、図柄、枠、筐体のパーツを生成して個別に管理する。操作用の文字、数値、選択状態、盤面レイアウトは引き続きHTMLとCSSで扱う。各パーツは実寸での識別性、見切れ、配信パス、読み込み失敗時の視認性を確認する。

## ⑤ 音素材を保存して追加する

④の組み込み後、調査で見た音の区切りと役割をベースにオリジナルの素材を制作する。回転開始、停止、成立、着地、希少成立、差引プラスの結果で音の意味を分ける。音素材をゲーム内に保存し、無音設定、音量、スキップ時の停止、プラスと元返し以下の聞き分けを確認する。
